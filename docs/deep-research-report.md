# Overview  
Designing a zero-cost browser-based character creation platform requires combining multi-view 3D reconstruction, mesh processing, rigging, and animation entirely with free tools and on-device compute.  Traditional photogrammetry (multi-view stereo) and new neural methods (NeRF/Gaussian Splatting) are the core image-to-3D approaches.  Photogrammetry (e.g. COLMAP/OpenMVG) is well-established and open-source (COLMAP is BSD-licensed), but normally needs many overlapping photos (each part of the subject should appear in **≥3 images**) to produce an accurate mesh.  Gaussian Splatting and NeRF methods (e.g. Luma’s 3DGS) can yield very realistic models from images with less manual setup and real-time rendering benefits, but they require heavy GPU training and dozens of images.  In practice, a *hybrid pipeline* is needed: rely on multi-view reconstruction (with COLMAP/AliceVision/Meshroom) when the user provides enough images, but fall back to **parametric human models** or silhouette-based meshes when only two images are available.  Any solution must clearly indicate uncertainty when views are insufficient.  

Free open-source tools can handle each stage. For example, AliceVision’s Meshroom (MPL-2.0 licensed) provides a node-based photogrammetry pipeline, and COLMAP (BSD-3-Clause) now even runs in the browser via WebAssembly.  For Gaussian Splatting, the **gsplat** library (Apache 2.0) implements Luma AI’s method in PyTorch.  Automatic retopology can use *Instant Meshes* (permissive BSD licence), or mesh fixers (e.g. CGAL, libigl) to yield a clean, manifold mesh.  Rigging can use open frameworks like Blender’s Rigify or SMPL-based methods; for example, SMPL-Body is CC-BY-4.0 (free with attribution), providing a skeletal model of the human body.  Motion assets can come from CC0 libraries (e.g. the KinemIQ free animations – 35 CC0 clips in FBX/GLTF).  Three.js (MIT licensed) or Babylon.js can power the browser viewer, supporting glTF/GLB import, skinning, and animation blending on web or mobile devices.  

Key challenges and constraints include supporting extremely limited input (e.g. only two photos), ensuring models are production-quality (clean topology, complete UVs, realistic proportions), and doing it without paid services or servers.  Achieving this requires an end-to-end design: guiding the user on image capture (lighting, angles, overlap), running reconstruction (client-side via WebAssembly or optional local scripts), then mesh cleanup/retopo, auto-rigging with labeled bones, a motion-editing UI with IK and blending, and finally export to glTF/FBX for engines.  All components must be free to use (no proprietary licenses) and ideally run in-browser or via optional local tools, so the user bears no cost.  We now examine each part in detail, citing open-source projects and standards.  

## 3D Reconstruction from Images  
- **Multi-view photogrammetry**: Using multiple photos of the character (front, side, back, etc.) with overlap is the most reliable free method.  Tools like COLMAP or Meshroom/AliceVision can recover camera poses and dense geometry.  COLMAP (now with a WASM port) can run feature extraction, matching, and sparse Structure-from-Motion in the browser.  For the mesh, AliceVision’s MVS and texturing nodes can be run offline (via Meshroom GUI or scripting) to produce a textured mesh.  These tools require decent image coverage – Rafael Spring (COLMAP-wasm) advises *“at least three images”* of every surface point.  If the user provides only two images (front and side), photogrammetry will be under-constrained; results will likely be incomplete or warped.  The UI should warn that *“two views alone cannot guarantee a complete 3D model”* and suggest extra photos for better results.  As fallback, we can initialize a generic human template (e.g. SMPL body) to fill missing geometry, acknowledging lower fidelity.  

- **NeRF / Gaussian Splatting**: Neural radiance fields (NeRF) and *3D Gaussian Splatting (3DGS)* represent the scene as a neural volume or point-cloud of anisotropic Gaussians.  These can render novel views and yield high detail, but require many input images and heavy training.  Gaussian splatting (Kerbl et al., 2023) dramatically sped up NeRF training and rendering and is now open-source (gsplat library, Apache 2.0).  Meshroom even offers an “MrGSplat” plugin to integrate 3DGS into its pipeline.  In theory, the browser app could export COLMAP data (camera poses, sparse points) to gsplat for neural optimization.  However, training still needs a powerful GPU and tens of images, so it’s unrealistic client-side.  For our zero-cost product, we would **not rely on cloud NeRF**.  Instead, Gaussian Splatting could be an *option* if the user has a capable PC with CUDA and many photos; we could provide an exportable gsplat PyTorch script and let advanced users run it locally.  Once trained, gsplat can generate a point-cloud with view-dependent colors.  We would then convert that to a mesh (via Poisson/ball-pivoting or any GS→mesh method).  Note: cutting-edge GS-to-mesh (AnyGS2Mesh, MeshSplats) is still research, so a practical pipeline is: densify with photogrammetry if possible, or let the user manually fix the GS output.  Overall, neural methods *enhance* results when data is plentiful, but the core solution is still mesh-first reconstruction from images.  

**Summary of imaging**: We recommend using open photogrammetry for multi-shot captures (browser COLMAP or Meshroom pipelines) and falling back to parametric shape-fitting for 2-shot input.  This avoids any paid API or server usage.  Crucially, we make *image guidance* part of the UX (see below) and flag when quality will be low.  If many images are available and the user has a GPU, optional integration with neural tools (gsplat via PyTorch or DPT for depth) can be offered but not required.  All processing should occur client-side or user-side to keep costs zero.  

## Mesh Cleanup, Retopology and Texturing  
Once a raw 3D scan or reconstruction is obtained (point cloud or high-poly mesh), it must be converted into a clean, watertight, game-ready mesh with proper topology and textures.  

- **Cleanup & Retopology**: Photogrammetry often yields noisy, dense meshes with irregular topology.  We can use free tools to fix them.  *Meshlab* (GPL) can remove outliers, fill holes, and simplify meshes.  *Instant Meshes* (BSD license) can re-mesh to a low-poly quad topology.  Also, *Blender* (GPL) has remesh and decimate modifiers and can sculpt-fill any missing parts.  Our pipeline could call a WebAssembly version of a remesher or instruct the user to download a small helper.  For example, an **OpenCASCADE** or **CGAL** WASM mesh-fixer could ensure watertightness.  The aim is to produce a *manifold* mesh of moderate polygon count (~5k–20k quads for a character) with uniform detail.  We should expose parameters (detail level, symmetry) and validate the result (e.g. no stray vertices or inverted normals).  

- **UV Unwrapping & Textures**: With a good mesh, the next step is UV mapping and texturing.  Tools like Blender or **xatlas** (MIT license) can auto-unwrap UVs.  If the photogrammetry pipeline produced images, we can bake textures from those photos onto the mesh.  Meshroom does texturing (patch-based fusion) which can be used.  Alternatively, transfer projected colors from the original images onto the mesh (preferably in the browser with Three.js rendering each texture).  We may also allow user-provided or procedural textures (e.g. skin base).  The final product must have a consistent diffuse/albedo map and optionally normal/bump maps.  Export formats like glTF support PBR materials, so we will output glTF/GLB with embedded textures.  

- **Quality Control**: Before rigging, validate the mesh: it should be watertight (check for holes), have one connected component per character, properly oriented normals, and reasonable edge lengths.  The system can run automatic checks (e.g. MeshLab’s “Measure Topology” filters) and warn the user if issues remain.  If badly formed, suggest re-running photogrammetry or adjusting retopo settings.  

## Skeleton, Rigging and Skinning  
With a cleaned mesh, we need to define a skeleton and skin it for animation.  

- **Skeleton Template**: We can use a standard humanoid skeleton (e.g. SMPL-Body skeleton) as a base. SMPL-Body (CC-BY-4.0) provides a 24- or 28-joint rig for a generic human.  We can scale or deform the SMPL skeleton to fit the scanned mesh by detecting key points (shoulders, hips, etc.) in the model or via a simple user-guided alignment UI.  Alternatively, use open libraries like **NPDM (Neural Pose)** or **Detectron3D** to estimate joints from the input images and infer the bone structure.  The goal is an *labeled skeleton* matching game conventions (pelvis, spine, clavicle, limbs, head, etc.).  The final rig should have named bones for easy animation retargeting (e.g. “Hips”, “Spine1”, “LeftArm”, etc.).  

- **Auto-Rigging Tools**: Blender’s Rigify (GPL) can automatically add a rig to a character mesh using templates, or **MakeHuman** (CC-BY) can generate a base mesh with rig which we could morph to fit the scan.  Some projects (e.g. SMPLify, HMR) fit SMPL models to images, yielding pose and shape – we could use those outputs to initialize the rig.  However, for zero-cost browser implementation, a simple auto-rig pipeline in JS/TS would be ideal: e.g. align a pre-made skeleton to the mesh and compute skin weights by proximity (distance to bone).  Libraries like **threejs-skeleton-helper** and **three.js Skeleton** can assist in this.  Weight painting could be approximated by each vertex taking the nearest few bones (with falloff) – many games use this for quick rigs.  In Blender (an optional companion tool), one can also use data transfer modifiers (Proximity) for weight painting, but we aim to minimize offline steps.  

- **Skinning/Weights**: Once bones are placed, compute vertex skin weights.  For example, project each vertex to nearby bones and assign influences based on distance or heat diffusion.  Algorithms like *Heat Diffusion Skinning* (Joshi et al.) can compute smooth weights automatically.  Alternatively, a simple metric (50% torso vs arm for shoulder region) may suffice.  The result is a skinned mesh where posing via bones deforms the mesh realistically.  Export the skeleton and weights with the mesh (glTF supports skinned meshes with up to 4 bone influences per vertex).  

- **Joint Limits & Constraints**: To ensure plausible motion, embed joint constraints.  Use common biomechanics data: e.g. elbows are hinge (~0–160°), knees similar; shoulders/hips are ball joints with limits (e.g. ±90°), spine twists ~±45°, etc.  We can hard-code typical ranges or use a biomechanics library.  These constraints will guide IK solvers and prevent unnatural poses.  Store this with the skeleton so the preview and any IK operations respect them.  

## Animation Library and Editing  
The platform should ship with a built-in library of animations and allow layering, blending, and part-specific editing.  

- **Animation Sources**: Use freely-licensed motion clips.  For example, the [KinemIQ CC0 library](https://github.com/Kinemiq/free-game-animations) provides dozens of humanoid animations (walk, run, idle, jump, etc.) under CC0, exportable as glTF/FBX with 66-bone rig.  We should incorporate a curated subset of such motions.  Additionally, open resources like CMU Motion Capture (public domain) or Mixamo’s free-licensed motions could expand the set, but we must respect licenses.  All clips should target a generic humanoid skeleton; retargeting code will map them to our user’s custom rig.  

- **Organization**: Categorize animations by body part and action type: e.g. *Full-body* (walk, run, jump), *Upper-body* (wave, punch), *Lower-body* (kick, walk in place), *Gestures* (nod, shrug).  The UI should let users select animations or apply partial clips.  For example, one could select a “Clap” gesture affecting only arms, and it would play layered on the base idle pose.  

- **Blending and Layers**: Implement animation blending (morphing between clips) and additive layering.  Use techniques like blend trees or linear interpolation on bone transforms.  For part-based motions, use *masking*: e.g. an “arm wave” clip applies only to the arm joints while the rest of the body holds an idle animation.  Three.js AnimationMixer or Babylon.js AnimationGroups support blending.  The UI could let the user drag in multiple clips on a timeline or graph, with opacity sliders for mixing.  We must also handle foot planting and in-place motions (e.g. remove root motion from canned clips if necessary).  

- **Inverse Kinematics**: Include IK for interactive posing.  For example, allow the user to grab the character’s hand and move it, and compute joint rotations (using CCD or FABRIK algorithms) while respecting joint limits.  Open-source JS libraries (like *threeik*) can provide 3DOF shoulder/elbow/hand IK.  This helps refine animations or create new ones (e.g. pointing at objects).  

- **Biomechanical Realism**: To keep poses natural, enforce the joint limits set earlier.  Additionally, implement simple coordination: if both feet are planted, hip motion should accommodate.  Advanced: a spine model with inverse dynamics (bending forward when arms raise) could be added, but even a basic parent-child joint chain with limits yields reasonably plausible motion.  Because perfect realism is hard, provide a “gait/skeleton preview” mode: side-by-side display of the source clip and the retargeted pose on the user model, as requested.  For example, show two small viewers – one playing the original mocap skeleton, one playing the user character in sync – so differences in limb length or rigging are obvious in real time.  

- **Live Preview**: Implement a split-view in the UI.  On the left, display the source motion (e.g. a reference skeleton or a proxy model), on the right the user’s character with the applied animation.  As the user tweaks blending or constraints, both update.  This is critical for iterative adjustment.  Performance should target smooth 30–60 FPS on modern browsers.  

## Client-side Browser Architecture  
- **Core Stack**: The front-end is a web app (React or Vue) using **Three.js** (MIT) for 3D rendering.  Three.js supports loading glTF/GLB with skins and animations, and has helpers for cameras, controls, and shaders.  For mobile compatibility, we ensure a responsive UI (CSS media queries, touch controls).  No plugins (WebGL 2 or WebGPU preferred).  

- **Image Input & Preprocessing**: The user uploads JPEG/PNG images (front, side, optional back/extra).  The browser previews them.  Optionally, run a WebAssembly module for Structure-from-Motion (e.g. colmap-wasm) to compute camera intrinsics/poses and sparse points.  The COLMAP wasm (or a JS wrapper) can do SIFT, matching, and sparse mapping fully client-side.  If available, also run a monocular depth estimator (e.g. a lightweight ONNX model via WebGPU) on each image to guess geometry.  These produce initial point clouds/depth maps.  

- **Geometry Reconstruction**:  If the user provided 3+ images and the browser has enough memory, we attempt dense reconstruction.  Currently, webColmap supports sparse only; we must handle dense differently.  One approach is: use feature matches to guide a multi-view stereo algorithm (like WebGL-accelerated plane-sweeping, or Poisson reconstruction from fused depth).  If not practical, prompt user to run an external photogrammetry (e.g. Meshroom desktop) and import the result.  The application can import a pre-generated mesh (glTF/OBJ) if the user already has one.  

- **Mesh Cleaning**:  After initial mesh is in the browser (via glTF import), run JS or WASM mesh analysis: compute normals, find holes, simplify if needed.  We can integrate libraries like *meshoptimizer* or *three-mesh-bvh* to simplify/optimize the geometry on the fly.  For remeshing, we may rely on the user using an offline tool (offer a “Fix in Blender” export).  Emphasize that mesh cleanup is critical, and provide diagnostics (e.g. “Mesh has 5 holes, consider re-run capture or manual fix”).  

- **Rigging UI**: Provide an interface to align a default skeleton.  For example, overlay a 3D skeleton gizmo on the mesh and let the user drag joints (hips, knees, shoulders) into place.  Once placed, compute skin weights automatically.  This can use Three.js raycasting for picking bones on the model.  Real-time preview of “pose the skeleton” helps user fit it.  

- **Animation & IK**: Use Three.js’s AnimationMixer for blending clips.  The UI for animation editing can be a web-based timeline (HTML canvas or libraries like *react-timeline*) where clips are arranged and layered.  For IK, include a small interactive mode: clicking and dragging an end-effector moves it via IK solver (like CCD, implementable in JS).  Bones should obey limits as coded.  Provide quick controls (sliders) for adjusting global motion parameters (e.g. “speed”, “blend weight”) in real time.  

- **Export**: Finally, allow exporting the character as glTF/GLB with skin and all animations baked.  Three.js can serialize the skinned mesh and animations.  We should also support downloading FBX for engines: either use a JS FBX exporter (though fewer exist) or instruct user to convert glTF to FBX using Blender.  The UI can have “Export for UE4/Unity/Godot” buttons with instructions (e.g. “Import the GLB into Godot directly, use FBXImporter in Unity”).  

- **Storage & Privacy**: All assets (images, intermediate data, models) should stay local unless the user explicitly shares.  Use browser IndexedDB or local filesystem API (via FileSystemAccess) for caching project data.  No uploads or external APIs.  Users can save a project file (JSON with images/poses) or exportable assets.  This ensures no hosting costs and respects privacy.  

- **Performance Targets**: The app should remain responsive on a typical modern laptop or high-end phone.  Keep polygon counts modest.  Offload expensive math to WebAssembly or GPU (WebGL/WebGPU).  If a step is too slow (e.g. dense reconstruction), fall back to “please wait” dialogs or allow asynchronous completion (Web Workers).  Test memory usage on Firefox/Chrome on Android.  Provide “Low Quality” mode (reduce texture resolution, use mipmaps) for older devices.  

## Costs, Licenses, and Compute Requirements  
Every component must be open/free:  

- **Software Licenses**: We use only OSS components: Three.js (MIT), the web app framework (MIT), open photogrammetry (COLMAP – BSD 3-Clause; AliceVision – MPL-2.0), gsplat (Apache 2.0), Instant Meshes (BSD), etc.  Animation clips (KinemIQ) are CC0.  Note: SMPL-Body is CC-BY-4.0, which is free but requires attribution; we should display a credit line for any included SMPL usage.  There are *no* proprietary engines or paid services.  The only possible cost is developer time and any modest hosting (the app could be static-hosted on GitHub Pages or an inexpensive CDN).  

- **Compute**: Rendering and light processing are done on the client GPU/CPU.  Heavy tasks (dense SFM, neural net inference) may be too slow on mobile.  For densification, we can optionally let the user pre-generate data on their PC (Meshroom with GPU) and upload the result.  Otherwise, rely on approximations (depth from two images, etc.).  We must clearly communicate that some ideal features (e.g. perfect NeRF from 2 images) cannot be achieved for free.  The browser COLMAP port shows that sparse SFM *is* feasible in-browser with WebGPU, which we will leverage.  Gaussian Splatting training is GPU-heavy; we will offer it only as an **offline** option for advanced users.  

- **Zero-cost Architecture**: The entire tool can be a static web app with client-side code and asset imports.  No backend servers or cloud computing are required.  If we host any JS libraries, it could be via CDNs.  This means truly zero marginal cost per user.  If special compute is needed, it’s on the user’s device.  The architecture could optionally include a companion desktop app (e.g. Electron) that bundles heavier binaries (Meshroom, etc.), but we must make it clear this is optional.  

- **Platform Support**: The tool targets modern browsers (Chrome/Firefox on desktop/mobile).  We’ll recommend WebGL2 and optionally WebGPU if available for performance.  No native iOS Safari WebGPU yet, but polyfill or degrade gracefully.  We should test on Android.  All chosen libraries (Three.js, Colmap-wasm, etc.) run in these environments.  Animations and GLTF are widely supported.  

- **Licensing Constraints**: Apart from attribution for CC-BY content (e.g. SMPL-Body), all components permit commercial use.  glTF and FBX are de facto standards (glTF is open-licensed by Khronos).  Autodesk’s FBX SDK is proprietary, so for FBX export we either use open converter scripts or rely on Blender (GPL) to convert glTF to FBX, which is a one-off user step.  

## Phased Implementation Plan  
1. **MVP – Image-to-Mesh (Browser).** Implement image upload and basic SFM.  Integrate colmap-wasm to compute camera poses and a sparse point cloud.  Display the sparse points as dots.  Allow exporting this (or dense cloud) for offline use.  In parallel, allow importing an offline mesh (OBJ/glTF) so users can skip if needed.  
2. **Mesh Generation & Cleanup.** Automate surface reconstruction: for example, run Poisson reconstruction (via WASM) on sparse cloud, or surface via Blender script (if local).  Integrate a remesher (like Instant Meshes via WASM).  Provide UI to run mesh cleaning and auto-UV.  Validate with test cases (monkey, bust, full char).  
3. **Auto-Rigging.** Build a tool to align and place a default humanoid skeleton.  Use SMPL or a custom bone structure.  Implement weight skinning automatically.  Offer user adjustment sliders for bone lengths.  Test by loading known models (MakeHuman templates) and verifying skin deforms correctly.  
4. **Animation & Preview.** Import CC0 animations (converted to glTF).  Create an animation editor where user can choose clips, blend weights, and see the character animate.  Implement side-by-side preview of source vs char.  Add simple blending and looping.  Integrate IK for one-limb adjustments.  
5. **Advanced Editing.** Add layering of animations (e.g. mix “arm wave” on top of walking).  Implement timeline UI with blend controls.  Enforce joint limits in real-time.  Optimize performance.  Allow user to paint or adjust skin weights if needed.  
6. **Export & Integration.** Finalize export: glTF/GLB of skinned mesh with animations.  Add buttons/instructions for Unity/Unreal/Godot (e.g. “Unity: import via FBX”).  Test by loading exports into Godot (native GLTF), UE4 (GLTF plugin or convert to FBX), and verifying skeleton/animation.  
7. **Quality Assurance.** Each stage has acceptance criteria: photogrammetry should reconstruct basic shapes for test image sets (e.g. make sure a sphere and cube scan correctly).  Meshes must have <X% holes, correct normals.  Rigging must place shoulders near shoulders, knees at leg midpoints.  Animations must play smoothly at >30 FPS on mid-range devices.  Perform user testing with a set of photo pairs, and refine UI prompts.  

## Handling Two-View Limitations and Uncertainty  
With only two images, full 3D reconstruction is fundamentally ambiguous.  The system will therefore:  
- **Warn** the user that accuracy will be limited if fewer than ~5 images are provided.  Display a “confidence” meter or highlight unresolved areas (e.g. back of the model).  
- **Fallback modeling**: Use the two silhouettes (front and side) to carve out an approximate shape.  For example, extrude the average silhouette depth and blend with the side view profile.  Then fit this coarse mesh to a parametric human model (SMPL-Body) to make it resemble plausible anatomy.  Allow the user to tweak major dimensions (e.g. chest/waist width) via sliders.  
- **User-guided correction**: Provide manual sculpting tools in the browser (e.g. using Three.js’s `BufferGeometry` editing) or via a link to an offline sculpting (Blender) for the user to refine the shape.  The app should mark uncertain regions (in red) and invite the user to correct them.  For example, if the side view doesn’t cover the arms, the system might default the arms to average width but allow manual adjustment.  
- **Role of Gaussian Splatting**: In the two-image case, Gaussian Splatting offers little advantage, since it requires many views.  We would *not* attempt GS on two images.  Instead, GS could be used if the user later provides more images.  If someone insists, an experimental web demo could allow them to run a pre-trained GS inferences (unlikely feasible).  In short, the system should not pretend to solve two-view completeness magically.  

## Biomechanics and Joint Modeling  
To ensure realistic motion, the platform will incorporate basic biomechanical joint models:  
- Each joint type (ball-and-socket, hinge, pivot) will have preset limits.  For example, the elbow is a hinge (0–160°); the shoulder is a ball joint (rotation up to ~170°, abduction ~120°).  These ranges will be hard-coded from anatomical data.  When applying animations or IK, we clamp joint rotations to these limits.  
- For coordinated motions (like walking or reaching), we will rely on the motion data itself and blending rather than physics simulation.  We do not need full inverse dynamics; simple pole-vector constraints (e.g. keep the knee forward) suffice.  If a user tries an impossible pose, we either snap the joint to its limit or reject it with a warning.  
- We will document the joint limits used (either in credits or a help section) so advanced users know how our character compares to real anatomy.

## Security, Privacy, and Testing  
All processing is local; no user data is transmitted. The app should use HTTPS and standard web security (CSP, sandboxing). User images and models remain in browser memory/storage. Project files may be optionally encrypted if stored remotely (e.g. Google Drive), but default to local-only.  

QA testing will use diverse datasets: human photos (varying clothing, poses, multiple angles) and different devices (desktop, Android, iPhone). Acceptance criteria include: end-to-end successfully producing a rigged animated glTF from example inputs, performance benchmarks met, and correct licensing declarations.  

## Conclusion  
The recommended build path is to leverage proven open-source pipelines (COLMAP/Meshroom for capture, Instant Meshes for retopo, SMPL for skeleton, Three.js for rendering) and integrate them into a cohesive web app.  The two-image case remains inherently limited: we will manage expectations and offer manual adjustments rather than claiming full automation. By combining existing OSS tools (as summarized above) and developing the necessary bridging code (e.g. JS wrappers for processing, UI flow, blending systems), we can deliver a **production-quality browser character creator** with **zero cost** to the user. All steps will be validated with citations and test cases (e.g. [16†L133-L136] for capture guidance, [23†L197-L205] for animations, [24†L37-L44] for evaluating GS viability). Robust exports to glTF/GLB (and documentation for engine import) ensure the result is game-ready. The phased plan above, along with the cited open-source precedents, provides a clear roadmap to implementation.
